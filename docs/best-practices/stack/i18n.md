# Internationalization (i18n) Best Practices

This document covers the portable doctrine for internationalizing user-facing
copy, plus one fully worked example for this repository's stack (Angular 11 +
@ngx-translate). Adopt the doctrine on any stack; the worked example is
specific to this project. See "What is portable / not portable" below for the
line between the two.

---

## Doctrine (stack-agnostic)

These rules apply regardless of language or UI framework:

- **No hard-coded user-facing literal string in UI markup.** Copy lives in a
  catalogue and is resolved by key lookup at render time, not written inline
  in a component/template.
- **Catalogues have a primary locale and at least one fallback locale.**
  Ship both together; do not leave a translation missing in the fallback
  because the primary locale changed first. Add or update every locale file
  in the same change.
- **Enforcement must be machine-checked, not prose.** A style-guide sentence
  that says "don't hard-code strings" does not hold once a codebase has more
  than a handful of screens. The convention needs an automated check — a
  lint rule, a static scanner, or an equivalent CI gate — that fails a PR
  containing a violation. Do not add a suppression escape hatch (an
  `eslint-disable`-equivalent) to get a screen merged; put the string in the
  catalogue instead.
- **The enforcement mechanism itself is subject to
  [planted-violation-proof discipline](../3-testing.md#planted-violation-proofs).**
  Introducing or materially modifying the check that catches hard-coded
  strings (the lint rule config, a custom key-extraction scanner, or
  equivalent) requires the same fails-when-present / passes-when-absent
  proof, at a concrete file and line, as any other automated check. A
  described-but-unexercised i18n lint rule is a declared-but-unverified
  control, not a working one.
- **Data-driven copy goes through the same catalogue discipline as static
  copy.** When user-facing text originates in the database (a stored enum
  value, an error code, a category label) rather than in markup, resolve it
  through the catalogue by a stable code — never persist the already-
  translated display string. The same rule applies to values that are
  locale-resolved from a data row (e.g., a label stored per-locale in a
  table): resolve by the active locale, falling back to the primary locale,
  the same way a static catalogue lookup falls back.
- **Currency, dates, and numbers are not catalogue strings.** Route them
  through the platform's locale-aware formatting facility (e.g. `Intl` in
  JS/TS) parameterized by the active locale, rather than hand-writing a
  per-locale format table. Verify the platform's locale output actually
  matches the target format (decimal/thousands separators, month names) —
  do not assume the default matches the mockup.

## Worked example: Angular 11 + @ngx-translate

> **This section is this repository's stack, replacing the upstream template's
> React Native + i18next example.** The doctrine above is the portable part.

### Stack

| Concern              | Choice                                                                 |
| -------------------- | ---------------------------------------------------------------------- |
| Runtime              | `@ngx-translate/core` 13                                               |
| Catalogue loader     | `@ngx-translate/http-loader` 6 (fetches catalogues over HTTP at runtime) |
| Catalogue location   | `src/assets/i18n/en.json`, `src/assets/i18n/es.json`                    |
| Primary locale       | `en`                                                                   |
| Fallback locale      | `en` (via `setDefaultLang`)                                            |
| Locale detection     | `translate.getBrowserLang()` matched against `/en|es/`                 |
| Enforcement          | **None today — see "Enforcement gap" below**                           |

### Catalogue and resolver wiring

The loader factory is defined and **exported** from `src/app/app.module.ts`:

```ts
export function HttpLoaderFactory(http: HttpClient): TranslateHttpLoader {
  return new TranslateHttpLoader(http, './assets/i18n/', '.json');
}
```

The root module registers it with `forRoot`; every lazy feature module must
import that same factory and register it with `forChild`:

```ts
// In each lazy module (about, coffee, experience, hobbies, projects)
import { HttpLoaderFactory } from 'src/app/app.module';

TranslateModule.forChild({
  loader: { provide: TranslateLoader, useFactory: HttpLoaderFactory, deps: [HttpClient] },
});
```

> **Failure mode**: a lazy module that omits `forChild` renders raw key strings
> (`HEADER.HOME`) instead of copy. If you see uppercase dotted identifiers in the
> UI, this is the first thing to check.

Locale selection happens once, in `AppComponent`'s constructor:

```ts
translate.addLangs(['en', 'es']);
translate.setDefaultLang('en');
const browserLang = translate.getBrowserLang();
translate.use(browserLang.match(/en|es/) ? browserLang : 'en');
```

### Usage patterns

```html
<!-- Preferred: the pipe, in templates -->
<a>{{ 'HEADER.HOME' | translate }}</a>

<!-- With interpolation params -->
<p>{{ 'ABOUT.BIOGRAPHY.P1' | translate: { yearsOfExperience: yearsOfExperience } }}</p>
```

```ts
// In component code, when the value is needed imperatively.
// Prefer get()/stream() — instant() returns the key if the catalogue
// has not loaded yet, which is a real race on first paint.
this.translate.get('CONTACT.SUCCESS').subscribe((msg) => this.show(msg));
```

### Conventions for this repository

- **Keys are uppercase, dot-namespaced by feature**: `HEADER.*`, `FOOTER.*`,
  `ABOUT.*`, `CONTACT.*`, `PROJECTS.*`. Keep a new key under the namespace of the
  feature that renders it.
- **Add every key to both catalogues in the same commit.** A key present only in
  `en.json` silently falls back; a key present only in `es.json` is dead weight.
- **Re-read language-dependent component state on language change.** Several
  components subscribe to `translate.onLangChange` and rebuild derived arrays.
  `LandingComponent` currently duplicates its 13-entry skills array verbatim in
  both `ngOnInit` and the `onLangChange` handler — when editing that data, change
  both copies, and prefer extracting a single method over adding a third copy.
- **Language is not persisted.** Unlike the theme (`localStorage.theme`), the
  selected language is re-derived from the browser on every load. If persistence
  is added, mirror the theme service's pattern rather than inventing a new one.
- **Locale-aware numbers and dates go through `Intl` or Angular's pipes**, never
  through per-locale catalogue entries. `moment` is already used for humanized
  durations on `/experience`.

### Known live defect

`en.json` defines `MESSAGE_CHARACTERS` while `es.json` defines
`MESSAGE_CHARACTE1RS`. The Spanish catalogue therefore falls back for that key.
Fix it when next touching contact-form copy, and do not replicate the typo.

### Enforcement gap

The doctrine above requires that the no-hard-coded-strings rule be
**machine-checked**. This repository currently has no such check: `tslint.json`
carries no i18n rule, and the framework's `scripts/lint/` helpers only lint
markdown, changelogs and shell — none of them inspect Angular templates.

Until a check exists, the convention is prose and will erode. Two viable
options, in rough order of effort:

1. **A key-parity script.** Parse `en.json` and `es.json`, fail on any key
   present in one and absent from the other. Cheap, catches the class of bug that
   already exists, and needs no lint infrastructure.
2. **A template scanner.** Flag literal text nodes in `src/**/*.html` that are
   not inside a `translate` pipe call. Higher value, higher false-positive rate;
   needs a suppression-free allowlist for things like brand names and icons.

Whichever is adopted, the check itself must carry a
[planted-violation proof](../3-testing.md#planted-violation-proofs): demonstrate
it failing on a deliberately introduced violation at a named file and line, and
passing once removed. A described-but-unexercised check is not a control.

## What is portable / not portable

| Bucket | Content | Applies to |
| --- | --- | --- |
| **1. Portable doctrine** | No-hard-coded-string rule, primary + fallback locale catalogues, "enforcement must be machine-checked," planted-violation-proof discipline applied to the enforcement mechanism itself, data-driven-copy-through-catalogue pattern | Any stack, any language |
| **2. Stack-specific worked example** | The `@ngx-translate` loader-factory wiring, the `forRoot`/`forChild` split across lazy modules, the uppercase dot-namespaced key convention, and the two proposed enforcement checks | Angular + @ngx-translate projects specifically — adapt or replace for another stack |
| **3. Not portable at all** | The actual runtime source files, their test suites, and the specific catalogue content of any one application | Stays in that application's own repository; not a template concern |

A project adopting this convention should implement bucket 1 always, adopt
bucket 2 only if its stack matches (or adapt the pattern to its own stack),
and never expect bucket 3 to be shipped by a framework template.

## Source

The **doctrine** section is carried unchanged from the upstream framework
template (`lhpaul/ai-dev-framework-template`), where it was derived from
`lhpaul/personal-finances` issue #34 and its implementation PR
[#41](https://github.com/lhpaul/personal-finances/pull/41). In that project the
enforcement rule was verified with a planted-violation transcript: a run on the
clean tree passes, a run with one deliberate literal string planted in a
component fails naming the exact file and line, and removing it restores the
pass.

The **worked example** section was rewritten for this repository during the
framework integration. The upstream template ships a React Native + Expo +
i18next example, which does not apply here; it was replaced with the Angular 11
+ `@ngx-translate` wiring this project actually uses. Everything in that section
was read from the source (`src/app/app.module.ts`, the lazy feature modules, and
`src/assets/i18n/{en,es}.json`) rather than adapted from the template.

Note the status difference: upstream, this document describes a *working,
proven* enforcement mechanism. Here it does not — see "Enforcement gap" above.
This repository has adopted the doctrine but has not yet implemented a check, so
`REVIEW.md`'s conditional i18n checklist cannot be satisfied by pointing at an
existing control.
